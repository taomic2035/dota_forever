# M10 经验/赏金数值校准审计(对照经典 DotA 1)

日期: 2026-06-12 · 范围: `src/data/balance.ts` 全部经济/经验/赏金相关常量与函数
方法: 只读 balance.ts + 精确计算,对照经典 DotA 1(WC3 引擎 6.x 系列)参考数值

---

## 摘要

本次审计发现 **5 处需修正的偏差** 和 **6 处数值完全匹配** 的项目。
最严重的两处是升级曲线低档(低等级仅 50–70% 的经典 XP 需求)和英雄击杀 XP 只有经典的 61–88%,两者共同导致**前期升级过快约 30–40%**。其余偏差中等程度:工资(正补)偏低 25%、XP/赏金共享半径偏大 30%、连杀封顶偏低。

## 一、升级经验曲线(XP_TABLE)

| 项目 | 当前值 | 经典 DotA 1 参考值 | 偏差 | 建议修正 | 风险 |
|------|--------|-------------------|------|----------|------|
| **XP_TABLE 公式** | `acc += 100 + (lvl-2)*110` | `acc += 200 + (lvl-2)*100` | 低档偏低 50%(Lv2)→ 收敛于 Lv12 (100%) → 高档偏高 5% | 改为 `200 + (lvl-2)*100` | 高:需平衡回归 |

### 详细对比(累计 XP)

| 等级 | 当前累计 XP | 经典 DotA 1 累计 XP | 当前/经典 | 说明 |
|------|-----------|-------------------|----------|------|
| 2 | 100 | 200 | **50.0%** | 一级升二级极快 |
| 3 | 310 | 500 | **62.0%** | |
| 4 | 630 | 900 | **70.0%** | |
| 5 | 1,060 | 1,400 | 75.7% | |
| 6 | 1,600 | 2,000 | 80.0% | |
| 7 | 2,250 | 2,700 | 83.3% | |
| 8 | 3,010 | 3,500 | 86.0% | |
| 10 | 4,860 | 5,400 | 90.0% | |
| 12 | 7,150 | 7,700 | 92.9% | |
| 15 | 11,410 | 11,900 | 95.9% | |
| 20 | 20,710 | 21,000 | 98.6% | 中后期几乎对齐 |
| 22 | 25,200 | 25,200 | **100.0%** | 精确交叉点 |
| 25 | 32,760 | 32,100 | 102.1% | 25 级略慢 |

**关键发现**: 偏差集中在 Lv2–10 早期(50–90%),这正好是 lane 阶段最关键的窗口。
现行公式等效于「起点仅需一半 XP,斜率(110/级)却比经典(100/级)更陡」。
经典曲线每级递增 100 XP,公式为 `200 + (lvl-2)*100`,Lv2–19 精确对齐,Lv20–22 经典有一段平台期(均 2100 XP/级),Lv23+ 重新递增(2200/2300/2400)。

**建议修正公式**:
```typescript
// 精确复刻经典 DotA 1
acc += lvl <= 19 ? (200 + (lvl - 2) * 100) : [2100, 2100, 2100, 2200, 2300, 2400][lvl - 20];
```
或直接硬编码经典 24 个增量值以完全精确。

## 二、英雄击杀经验(xpForKillLevel)

| 常量/函数 | 当前公式 | 经典 DotA 1 | 偏差 | 建议修正 | 风险 |
|-----------|----------|------------|------|----------|------|
| `xpForKillLevel` | `100 + victimLevel * 20` | `100 + victimLevel * 36` | **61–88% of classic**(Lv1 最接近,高等级差距越大) | 改为 `100 + victimLevel * 36` | 中:与 XP_TABLE 修正联动 |

### 详细对比

| 受害者等级 | 当前 XP | 经典 XP | 当前/经典 |
|-----------|---------|---------|----------|
| 1 | 120 | 136 | 88.2% |
| 5 | 200 | 280 | 71.4% |
| 10 | 300 | 460 | 65.2% |
| 15 | 400 | 640 | 62.5% |
| 20 | 500 | 820 | 61.0% |
| 25 | 600 | 1,000 | 60.0% |

**说明**: 击杀高等级英雄的 XP 奖励严重偏低;在经典 DotA 1 中,击杀 25 级英雄可获 1000 XP(单英雄独享),是重要的追赶机制。当前仅 600 XP 削弱了这一翻盘窗口。

> 注意: 经典 DotA 1 的击杀 XP 在多英雄靠近时是「总量分配」还是「每人均享」目前有歧义。
> 建议修正后结合 `XP_SHARE_RADIUS` 一并验证分配逻辑是否需要改为「总量 / 共享英雄数」。

## 三、经验共享半径(XP_SHARE_RADIUS)

| 常量 | 当前值 | 经典 DotA 1 | 偏差 | 建议修正 | 风险 |
|------|--------|------------|------|----------|------|
| `XP_SHARE_RADIUS` | 1300 | 1000 | **+30%(面积 +69%)** | 改为 1000 | 中 |
| `ASSIST_RADIUS` | 1300 | 1000 | +30% | 建议同步改为 1000 | 低(独立) |

**影响**: 半径 1300 使共享 XP 的覆盖面积是经典的 1.69 倍。经典 DotA 1 中 1000 单位是刻意的较小范围,使组团刷野时 XP 分散效果更明显。当前过大半径削弱了「离开 XP 范围单独行动」与「多英雄共享同一波兵」之间的对局选择权。

## 十、建议:低风险直接改 vs 需平衡回归验证

### 可低风险直接修改(不改游戏节奏结构,只修正数值对齐)

1. **`XP_SHARE_RADIUS` 1300 → 1000**:独立常量,只影响共享范围,无跨系统耦合。改后运行 `npm run batchsim` 基本验证即可。
2. **`ASSIST_RADIUS` 1300 → 1000**:同上,与 XP_SHARE_RADIUS 保持一致。
3. **连杀赏金上限 300 → 500**:仅改 `Math.min` 的上限参数,影响面小(高连杀场景罕见)。
4. **`CREEP_UPGRADE_INTERVAL` 450 → 600**:独立常量,只延迟兵线强化节奏,不影响伤害/赏金计算逻辑。

### 需平衡回归验证(`npm run batchsim`)后再修改

5. **`XP_TABLE` 公式修正**(最高优先级):
   - 建议改为 `acc += 200 + (lvl - 2) * 100`(Lv2–19 精确匹配经典,Lv20+ 可选用硬编码经典增量值)
   - 影响全局升级速度,与技能解锁时间、物品时机、胜负判断强耦合
   - 修正后英雄达到 Lv6 需要多 400 XP(约需多 6–8 分钟 lane 时间),节奏影响显著

6. **`xpForKillLevel` 系数 20 → 36**:
   - 与 XP_TABLE 修正联动(升级变慢后,击杀 XP 的相对分量增加)
   - 建议与 XP_TABLE 同批修改,然后一起跑 batchsim
   - 还需确认击杀 XP 分配逻辑:若多英雄共享同一池,总量应为 `100+36*level` 然后分配;若每人均享则系数需要相应调低

7. **`heroKillBounty` 公式 `200+9*level` → `100+11*level`**:
   - 前期人头赏金大幅下降(Lv1 从 209 降到 111),整体经济节奏最敏感
   - 单独修改影响最大,需配合完整 batchsim 验证双方经济差异数据
   - 建议最后修改,或与工资间隔一同修改以保持经济总量平衡

8. **`PERIODIC_GOLD_INTERVAL` 0.8 → 0.6**:
   - 工资上涨 33%(75→100 金/分钟),整局额外 1000 金
   - 若不同步降低人头赏金,会导致总经济过高;建议与 heroKillBounty 修正配套修改
